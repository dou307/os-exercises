# 维护与更新

本文件说明如何重建数据、跟上上游、校验结果和回退。所有命令都在项目根目录执行。

## 1. 文件所有权

| 文件/目录 | 由谁生成 | 能不能手改 |
|---|---|---|
| `vendor/kaoyan-408-os/` | 上游快照 | **不能**，改了就破坏字节一致性 |
| `data/questions.json` | `scripts/import_questions.py` | 不建议，重跑会被覆盖 |
| `data/source-registry.json` | 同上 | **不能手改**，它是 ID 身份的权威 |
| `data/mappings.json`、`chapters.json`、`topics.json`、`study-defaults.json`、`overrides/errata.json` | `scripts/build_mappings.py` | 首章写在脚本的 `CH1_REVIEW` / `ERRATA`；第二章正式输入为 `data/reviews/ch2.json` |
| `tests/fixtures/samples/` | `import_questions.py --write-fixtures` | 只在确认提取结果变化合理后重写 |
| `app/` | 手写 | 可以 |
| `dist/` | `scripts/build.py` | 不要手改，会被删除重建 |

## 2. 常规重建

```powershell
python -X utf8 scripts/import_questions.py     # 读 vendor，写 data/questions.json 与登记表
python -X utf8 scripts/build_mappings.py       # 写映射、章节、知识点、勘误
python -X utf8 scripts/validate_dataset.py     # 十二类校验，必须全绿
python -X utf8 scripts/build.py                # 组装 dist/
```

`build_mappings.py --write-doc` 会同时重写 `docs/映射审核记录.md` 与 `docs/第二章逐题复核.md` 的逐题表格，并运行第二章独立复算，避免文档与数据脱节。

## 3. 题目 ID 的稳定性

- ID 规则：`c{章}-s{h2 序号}-{h3 序号或 0}-q{原题号}`，例如 `c1-s3-0-q009`。
- 首次写入 `data/source-registry.json` 后即冻结；重跑导入时优先复用登记表里的 ID。
- 上游插入/移动题目导致定位变化时，若内容哈希完全一致，会沿用旧 ID 并写入 `relocations`。
- 题号或小节变化且内容也变了，会分配新 ID；旧条目变为 `retired`，历史作答仍按旧 ID 保留。
- **不要**为了让数字好看去手工删 `entries`。删了就等于放弃历史作答的可追溯性。

## 4. 跟随上游更新

1. 在 `_work/upstream.git` 拉取新提交，先记录新旧提交号与文件差异。
2. 用明确提交重新生成快照（不能直接覆盖工作副本）：

   ```powershell
   git -c core.autocrlf=false --git-dir=_work/upstream.git archive <新提交> |
     tar -x -C vendor/kaoyan-408-os
   ```

   `vendor/**` 在 `.gitattributes` 里是 `-text`，必须保持原始字节。
3. 更新 `scripts/import_questions.py` 里的 `UPSTREAM["revision"]` 和数据集版本号。
4. 重跑导入与校验，检查 `_work/reports/import-report.json` 里的警告与 `relocations`。
5. 人工确认新增题、答案改动与疑似同题移动；需要时补 `ERRATA`。
6. 重跑 `--write-fixtures` 前先比对样本差异，确认不是截断或丢内容。
7. 更新 `docs/调查记录.md`、`docs/执行清单.md` 后再提交。

## 5. 校验脚本查什么

`validate_dataset.py` 的十二类检查：

1. 总数、分章数、题型分布、无 `.q` 容器数量；
2. 5 道特殊题的集合与"不生成自动判分"；
3. ID 唯一、与登记表一致、内容哈希一致；
4. 字段完整、答案与解析非空、单选选项键连续且含答案；
5. 正文无脚本、事件属性、外链、`<details>` 残留；
6. **题干前 60 字与答案文本能在来源正文中定位**（防截断、防编造）；
7. 每文件题数等于来源 `details.qa` 数量；
8. vendor 文件字节数与 sha256 未变；
9. 上游页面 135 处图片引用全部为本地非空文件；
10. 12 个真实复杂样本逐字段回归一致；
11. 760 道均有唯一主归属与有效知识点；
12. 解析自述“故选 X / 答案 X”与答案字段一致（当前 348 道可提取，0 矛盾）。

2026-10-23 起，校验还包含 `verify_source_content.py` 的独立全文与结构核对，覆盖全部 760 道；
来源字节检查覆盖 176 个文件。前 60 字定位仅是附加线索，不能单独证明无损提取。
稳定 ID 先按内容认领；定位不变而内容变化时会停止自动迁移，需审核版本差异，禁止直接更新固定样本来绕过。

```powershell
python -X utf8 scripts/verify_source_content.py
python -X utf8 -m unittest discover -s tests -p 'test_*.py' -v
```

### 6.1 线上验收与发布链路

```powershell
$env:BASE_URL = 'https://dou307.github.io/os-exercises/'
node tests\browser\acceptance.js
```

线上运行时"子路径 /dist/"两项自动跳过（线上本身就在 `/os-exercises/` 子路径下，由前面的加载检查覆盖）；
跳转导致的 `ERR_ABORTED` 不计失败，只统计连接失败与 4xx/5xx。

发布链路：push 到 `main` → Actions 构建 `dist/` → 先跑 `validate_dataset.py`，通过才上传产物并部署。
**数据校验不过就不会发布**，这是有意的闸门。

关闭线上站点（对外动作，先确认用户意图）：

```powershell
gh api -X DELETE repos/dou307/os-exercises/pages
gh repo edit dou307/os-exercises --visibility private
```

同时删除 `.github/workflows/deploy-pages.yml` 可停止自动发布。

## 7. 回退

- 代码与数据：`git revert` 或回到上一个提交后重跑构建。
- 学习记录：先在首页导出 JSON，再改数据；导入时会按题目 ID 合并，不会清空。
- 不要通过删除 `personal/`、清空 localStorage 或删除 `dist/` 来"修复"问题。
- 上游快照回退用 Git 还原 `vendor/`，不要手工改回。
